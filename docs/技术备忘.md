## 2. 显示器身份（§7.6）

### 7.6 显示器身份：不要依赖框架给的 monitor id

**本项目自己维护屏幕标识，不使用 Tauri/tao 的显示器标识。** 理由：tao 在 Windows 上的显示器 ID 获取方式被报告为不可靠（[tao#1102](https://github.com/tauri-apps/tao/issues/1102)）。而我们的每屏配置需要跨重启、跨热插拔稳定对应到同一块屏幕——一个不可靠的 ID 会导致"设置跑到别的屏幕上"。

自己建立 `MonitorKey`，由以下信息组合而成：

1. `IDesktopWallpaper::GetMonitorDevicePathAt` 返回的设备路径（这是 `SetWallpaper` 需要的那个 ID，天然是主键）
2. `EnumDisplayMonitors` + `GetMonitorInfoW` 给出的矩形与 `szDevice`
3. 适配器 LUID（可选，用于区分换过接口的同一块屏幕）

**必须实测的一点**：Lively 传给 `SetWallpaper` 的是 `Screen.DeviceId`，而文档要求的是 `GetMonitorDevicePathAt` 的返回值。两者是否等价直接决定 M3 的实现方式，属于 §13 R1 的 spike 内容——spike 里要明确打印出这两个值并做对比。

### M4 桌面层宿主窗口（已挂载验证）

第一版只验证**窗口能不能正确挂进桌面层**，内容先不管（纯色填充）。

实测结果（`--test-desktop-layer --for 16`）：

```
Progman 矩形 = (-960,-62) 3520x1707
我们的窗口   = (-960,-62) 3520x1707      ← 完全吻合
是否完全吻合 = True
父窗口       = Progman（一致=True）
z 序（先列出的在上）: SHELLDLL_DefView → 我们的窗口 → Shell 壁纸层
```

退出后窗口干净销毁（`Progman 下找不到窗口类 …`），进程退出码 0。

**样式踩坑记录**：本机 Wallpaper Engine 的壁纸窗口样式是
`WS_CHILD | WS_EX_LAYERED | WS_EX_NOACTIVATE`，但**我们无法创建带
`WS_EX_LAYERED` 的跨进程子窗口**。逐项对照实验矩阵：

| 组合                                  | 结果                            |
| ------------------------------------- | ------------------------------- |
| `WS_CHILD` 单独                         | 成功                            |
| `WS_CHILD + EX_LAYERED`                 | 失败 `ERROR_FILE_NOT_FOUND(2)`  |
| `WS_CHILD + EX_NOACTIVATE`              | 成功                            |
| `WS_CHILD + 两个 EX`                    | 失败 (2)                        |
| 创建后用 `SetWindowLongPtrW` 补 LAYERED | 失败 `ERROR_INVALID_HANDLE(6)`  |
| 挂到 Progman 下**显式传 hInstance**     | 失败 `ERROR_INVALID_HANDLE(6)`  |
| 挂到 Progman 下**不传 hInstance**       | 成功                            |

两个结论：
1. 连"先创建再补样式"也不行，所以不是创建时机的问题，而是这一层不允许。
2. `hInstance` 必须传 `None`。顶层窗口两种都行，只有跨进程子窗口这条路在意它。

**这不构成阻碍**：视频帧要走 DirectComposition 合成，那条路不需要分层窗口。
真正关键的是父子关系与 z 序，两者都已验证。

**踩坑方法记录**：`CreateWindowExW` 失败时 `GetLastError` 也返回 0、错误信息是
"操作成功完成"，完全没有信息量。真正有用的是**逐项对照实验**——
一次只改一个参数，从"能成功"逐步逼近"失败"，最后定位到 `WS_EX_LAYERED`。
单看错误码是查不出来的。

### M4 每屏一个宿主窗口 + DirectComposition（已跑通）

`--test-desktop-layer` 现在的行为：每屏一个宿主窗口挂到桌面图标层之下，
每屏各用一套 DirectComposition 合成、各显示一种不同颜色（便于一眼看出"哪块屏画对了"）。

实测（`--test-desktop-layer --for 14`）：

```
挂载中：2 个宿主窗口
  WindowsWallPaper 桌面层 \\.\DISPLAY1  (0,0) 2560x1440
  WindowsWallPaper 桌面层 \\.\DISPLAY2  (-960,-62) 960x1707
退出后残留：0 个（应为 0）
图形设备    : 硬件
位置核对    : 每块屏的窗口都落在自己的显示器矩形上
```

日志里对应的逻辑尺寸与系统的物理缩放：

| 屏 | 建窗口用的尺寸（逻辑） | 系统给出的物理矩形 | 缩放 |
| --- | ---------------------- | ------------------ | ---- |
| DISPLAY1 | 3840x2160 | (0,0) 2560x1440 | 1/1.5 |
| DISPLAY2 | 1440x2560 | (-960,-62) 960x1707 | 1/1.5 |

父窗口（Progman）客户区是 5280x2560 **逻辑**，系统把它缩放到 3520x1707 物理像素。

**这里我第三次差点又按推断改代码**：我写过一个"按显示器在布局里的占比去乘父窗口
客户区尺寸"的版本，理由是"显示器给物理像素、父窗口客户区是逻辑尺寸，两者差一个缩放"。
那个版本在本机**也得出相同结果**——所以它"能跑"。但实测确认的真实机制是
**系统按父窗口的 DPI 上下文缩放子窗口**，我们只负责报逻辑尺寸。两个算法在本机恰好等价，
换个屏的排列或缩放就未必。因此最终实现退回到最简单的一条：直接用显示器矩形，
把缩放留给系统。少推断一件事就少一个出错点。

**线程模型**：所有窗口与所有 DirectComposition 对象都在同一条专用线程上创建与使用。
我实测过"窗口在 A 线程、合成在 B 线程"确实能工作（`CreateTargetForHwnd` 与 `Commit` 都成功），
但微软文档并未承诺 `IDCompositionDevice` 线程安全（[官方页面](https://learn.microsoft.com/en-us/windows/win32/directcomp/directcomp-portal)
只说"operating independently of the UI thread"），而所有官方示例都是同线程用法。
因此选择"一条线程、一个消息循环、一套设备"，代价是换图要过一次通道——
但视频帧率由解码器驱动、不走这条通道，所以这个代价可以接受。

**坐标换算**：显示器给的是屏幕坐标，而子窗口的位置是**父窗口客户区坐标**。
用 `ClientToScreen(progman, (0,0))` 问出父窗口客户区原点在屏幕上的位置，相减即可。
不用 `MapWindowPoints` 的原因：本 crate 里它只有返回打包 `i32` 的原始版本
（x 在低 16 位、y 在高 16 位），要手工符号扩展才能表示负坐标，
而本机桌面原点确实在负坐标（-960,-62）——正是容易出错的情形。

### M4 尺寸来源（连续推断错了两次，最终以实测为准）

**结论：宿主窗口的尺寸取自桌面层（Progman）自己的客户区，本机 5280x2560（逻辑），
物理渲染为 3520x1707，与 Progman 矩形完全吻合。**

这段值得完整记下来，因为我在这里连续推断错了两次，而两次都是靠"把数字打出来"纠正的：

1. 先按"各显示器矩形的并集"算，得到 5280x2560（主屏 3840x2160 + 副屏 1440x2560）。
   日志里就写着 5280x2560，看起来合理。
2. 实测窗口**物理**矩形是 3520x1707，而 5280/3520 = 1.5 = 主屏缩放比例。
   于是我推断"并集把物理像素多算了 1.5 倍"，并据此改代码。
3. 但把四个数字在**同一个进程**里都打出来之后发现：本进程里
   `GetMonitorInfoW` 的并集与 `GetSystemMetrics` **一致**，都是 5280x2560。
   我先前看到的 4000x2560 来自**另一个 DPI 未感知的进程**（PowerShell），两者不可比。
   我拿两个不同进程的数据拼出了"不一致"这个结论。
4. 真相是：我们的窗口是 Progman 的**子窗口**，坐标空间属于父窗口；
   5280x2560 是逻辑尺寸，系统按 DPI 缩放成 3520x1707 物理像素，
   正好等于 Progman 的矩形。**两个"错误"其实互相抵消，结果恰好正确。**

最终的稳妥做法是不去推断缩放关系，直接问桌面层要客户区尺寸。
`monitors::virtual_desktop_layout` 保留为兜底（在本进程里两者一致，
但它是系统权威值，比手写并集更可靠）。

**教训**：跨进程比较同一系统的量（DPI、分辨率、坐标）是不成立的——
每个进程的 DPI 感知设置不同，同一 API 会给出不同的值。
必须把要比较的量在**同一进程**里打印出来再下结论。

### M4 视频解码（Media Foundation，已跑通）

**为什么是 Media Foundation 而不是 ffmpeg**：用户最初的约束是"不能在项目外下载任何东西"。
Media Foundation 是 Windows 自带的，零外部依赖、不需要往交付文件夹里塞几十 MB 的解码器。
代价是只支持系统装了解码器的格式（H.264/HEVC/AV1 在 Win11 上都有；MKV 容器之类需要另装）。

实测（`--probe-video <文件>`，测试视频用本机已有的 ffmpeg 在项目内生成）：

```
格式      : 1920x1080
帧率      : 30.000 fps（30/1）
跨距      : 7680 字节/行（紧凑应为 7680，无填充）
存储顺序  : 自上而下
一帧字节  : 8294400
解码      : 30 帧耗时 306.1 ms，平均 10.2 ms/帧
帧率预算  : 33.3 ms/帧 —— 跟得上
相邻帧间隔: 333333 (100ns) = 33.3 ms
--- 循环验证 ---
rewind() 调用成功
回开头后第一帧时间戳 = 0.067 s —— 确实回到了开头
```

10.2 ms/帧 对 30 fps 的 33.3 ms 预算有一倍余量，**单屏够用**；
但两块屏同时播 4K 会吃紧（CPU 解码，没走 DXVA 硬件解码）。
性能不够时的下一步是接 `MFCreateDXGIDeviceManager` 把 D3D 设备交给解码器，
不过那要求解码线程与桌面层合成线程之间的设备管理，比现在复杂。

**这一版故意没有走 DXVA**：先把"CPU 解码 → 上传到合成表面"整条链跑通，
再决定要不要为性能引入设备管理。一次只引入一个新的不确定性。

#### 三个踩到的坑（都写成了注释与测试）

1. **`PROPVARIANT` 的 `vt` 必须显式设成 `VT_I8`**。我最初写"零值初始化就等于
   `VT_I8(0)`，不必碰 union"——**错了**。零值的 `vt` 是 `VT_EMPTY(0)`，
   MF 收到它不知道跳到哪里，于是**什么都不做也不报错**。表现是 `rewind()` 报告成功、
   但下一帧时间戳是 1.067 s 而不是 0.067 s。这类"静默失效"必须有测试盯着，
   因此加了 `timestamp_variant_really_sets_vt_to_i8`。
   顺带记两个 API 细节：crate 里 `PROPVARIANT_0_0_0` 的 64 位成员叫 **`hVal` 而不是 `llVal`**；
   写入 `ManuallyDrop` 字段要显式 `*` 解引用。

2. **`MediaFoundation` 句柄必须是结构体字段，不能是局部变量**。
   我最初写 `let _mf = MediaFoundation::start()?;`，它在 `open()` 返回时就 drop 了，
   于是 `MFShutdown` 在读取器还活着时被调用——**日志顺序暴露了它**
   （"Media Foundation 已关闭"出现在诊断输出之前）。MF 关掉之后解码行为是未定义的。

3. **跨距要从媒体类型读，不要按 `宽*4` 猜**。这个坑我连错两次：
   看到缓冲长度 8355840 而"紧凑"尺寸是 8294400，就断定"每行有 64 字节填充"
   （8355840/1080 = 7744）——**又错了**。`MF_MT_DEFAULT_STRIDE` 报的是 7680
   （正好 `1920*4`），没有填充；那 61440 字节的差值是 8 行的大小，
   来自**缓冲容量大于所需**。规则是：信媒体类型报的跨距，拷贝长度夹到 `宽*4*高`。

4. **`IMFSourceReader::SetCurrentPosition` 的签名是 `(GUID, PROPVARIANT)`**，
   不是裸的 64 位位置——它和 `IMFPresentationClock` 上同名的方法是两回事。
   而且它的声明被 `Win32_System_Com_StructuredStorage` 与 `Win32_System_Variant`
   两个 feature 门控着：**不开 feature 时不是签名不匹配，而是方法压根不存在**。

### M4 视频帧上屏（已跑通）

`--test-video-frame <文件> [--for N] [--frame N]`：解出某一帧并显示在每块屏上。

**先做无并发版**是刻意的：视频播放一旦接上线程与节拍，出问题时无法区分是

实测：

```
视频格式  : 1920x1080，30.00 fps
解码      : 取到第 45 帧（时间戳 1.567 s）
DISPLAY1 已显示视频帧（1920x1080 → 3840x2160，缩放 12.3 ms）
DISPLAY2 已显示视频帧（1920x1080 → 1440x2560，缩放  5.6 ms）
退出后残留：0 个宿主窗口
```

#### 把缩放移出合成线程（一个真实的性能缺陷）

第一版把 CPU 最近邻缩放放在合成线程里做，日志立刻暴露了它：取第 45 帧用了
**472.9 ms**。原因是 1920x1080 → 3840x2160 是 4 倍像素，而这段代码跑在合成线程上——
把合成线程拖住会让窗口消息与后续帧一起排队，表现为"播放一会儿就卡、拖窗口没反应"。

改成**调用方缩放、合成线程只做搬运**：

| | 缩放耗时 |
| --- | --- |
| 缩放放在合成线程（第一版） | 472.9 ms（整帧路径，含解码） |
| 缩放移到调用方线程 | **12.3 ms**（4K 屏）／**5.6 ms**（竖屏） |

`present_pixels` 现在**尺寸不一致就报错**，而不是默默在合成线程上缩放。
这样"合成线程只做搬运"这个约定是被强制执行的，不靠自觉。

#### 解码正确性验证：导出帧看眼睛

数值断言很难测"解出来的画面对不对"——我不会预先知道测试视频某个像素的准确值。
因此加了 `--dump-frame <视频> --out <png> [--frame N]`，把一帧导成 PNG 用眼睛看。

实测导出的第 45 帧是 H.264 标准彩条（红/绿/黄/蓝/洋红/青），
左上角还带着 ffmpeg 烧进去的时间戳 `00:00:01.500` 与帧号 `45`，
与请求的第 45 帧、1.567 s **完全吻合**。

这一步同时验证了三件以前没验过的事：
- **通道顺序**（BGRA → RGBA 的转换是对的，颜色没串）；
- **跨距处理**（画面没有斜切错位）；
- **时间戳**（取帧位置正确）。

证据图：`docs/m4-video-frame.png`。

### M4 连续视频播放（已跑通）

`--play-video <文件> [--for N] [--paused]`：**每块屏一个解码线程**，按帧时间戳节拍循环播放。

实测（两块屏同时播同一个 1920x1080 H.264 视频 26 秒）：

| | DISPLAY1 | DISPLAY2 |
| --- | --- | --- |
| 帧率 | 29.4 → 29.8 fps | 29.4 → 29.8 fps |
| 总帧数 | 769 帧 | 771 帧 |
| 循环 | 5 次 | 5 次 |
| **落后重置** | **0 次** | **0 次** |
| 单帧耗时 | 32.4–33.9 ms | 32.4–33.4 ms |

**"落后重置 0 次"是节拍设计有效的证据**：单帧耗时 33 ms 正好卡在 33.3 ms 的预算上，
如果用"每帧睡固定时长"的朴素做法，累计误差会让播放持续变慢；
用绝对时间基准（第 N 帧应在 `开始时刻 + 该帧时间戳` 显示）则单帧抖动不累积。

两块屏帧数差 2，说明它们**各自独立**（共用一个解码器就会被迫同步）。

暂停也验过：`--paused` 启动时 10 秒内显示 **0 帧**。

#### 每屏一个解码线程的理由

设计需求就是"每屏独立的列表"，两块屏可能播完全不同的视频。共用一个解码器会让
两块屏被迫同步——一块慢另一块也跟着卡。因此每屏一个线程、各持一个 `VideoReader`。

#### 节拍为什么用绝对时间

朴素做法是每帧 `sleep(1/fps)`。解码本身要 10 ms 左右，累计误差会让播放越来越慢：
30 fps 下每帧多花 1 ms，一分钟后就慢了 1.8 秒（将来接音频时画面与声音会明显脱节）。

绝对时间基准下，落后**不跳帧**（壁纸不是实时通信，宁可慢一点也不跳），
但落后超过 [`MAX_LAG_SECONDS`]（1 秒）时重置基准——否则一旦落后，
之后每一帧都会判定为"已经晚了"，节拍就完全失效。

暂停恢复时也会重建时间基准：否则暂停期间累积的时间会让恢复后连续若干帧
都判定为"已经晚了"。

#### 一个被真实失败暴露的 bug：COM 初始化

第一次跑两块屏时，**DISPLAY1 完美（29.8 fps）、DISPLAY2 完全失败**，错误是：

```
打开视频失败：尚未调用 CoInitialize。
```

Media Foundation 依赖 COM，而**每个使用它的线程都要初始化 COM**。
我只在程序启动时（主线程）初始化过一次，而主线程恰好是第一个解码线程的所在线程，
所以第一块屏能跑、第二块报错。

这个失败的表象是"只有一块屏能播"，**很容易被误判成显示器或窗口的问题**；
实际原因与显示器无关。修法是让 `VideoReader::open` 自己初始化 COM
（`CoInitializeEx` + `COINIT_MULTITHREADED`），并把句柄存进结构体，
让配对的 `CoUninitialize` 在同线程发生。

用 MTA 而不是默认的 STA：MF 解码器在 MTA 下工作得最好，而 STA 要求线程泵消息，
我们的解码线程不泵消息——那会让跨套间调用挂住。

`CoInitializeEx` 返回**裸 HRESULT**（不是 `Result`），成功是 `S_OK(0)`，
而"此前已初始化"是 `S_FALSE(1)`——后者同样算成功，且**不能**配对
`CoUninitialize`。这两种情况都处理了。

### M4 未解疑点：Progman 子窗口的 DComp 内容未能被自动检测看到

#### 已确认的事实

| 事实 | 确认方式 |
| --- | --- |
| 窗口正确挂在 Progman 下 | `FindWindowEx` + `GetParent`，两级核对一致 |

#### 未能确认的事

**内容是否真的出现在屏幕上。** 三种自动检测都不可用：

- GDI `BitBlt`：看不到 DComp 内容；
- DXGI 桌面复制：结果不可重复（同一自检，一次 `#FF00FF`、下一次 `#000000`）；
- DWM 属性查询：`DWMWA_EXTENDED_FRAME_BOUNDS` 失败，但那是因为对象是**子窗口**——
  给窗口加上 `WS_EX_NOREDIRECTIONBITMAP` 之后依然失败，所以它不能用来判断
  "DWM 是否合成这个窗口"。

#### 我在这一段里连续犯了三次同类错误（记录下来以免再犯）

1. 把"`DWMWA_EXTENDED_FRAME_BOUNDS` 查询失败"当成"DWM 没合成我们窗口"的**确凿证据**，
   并据此推断缺 `WS_EX_NOREDIRECTIONBITMAP`。加了那个标志后信号不变，
   说明它失败的原因是子窗口身份。
2. 把桌面复制的一次采样（`#FF00FF`）当成可复现的判据，重跑就变成黑色。
   一个有时说 A、有时说 B 的检测，哪次结果都不该采信。
3. 把"并集算出的虚拟桌面尺寸"当成窗口应有的尺寸，并据此改代码；
   后来发现两个来源在**同一个进程**里其实一致，我拿的是**另一个进程**的数据。

三次的共同点：**把"能区分两种状态的信号"当成了"能证明我想知道的那件事的证据"。**
一个信号能区分，不等于它能证明。

#### 疑点排查到这一步的结论

`Progman` 带 `WS_EX_NOREDIRECTIONBITMAP`（"我没有重定向位图"）。我们的窗口是它的
**子窗口**，而 DirectComposition 的 `CreateTargetForHwnd` 对子窗口是否真的会把内容
合到屏幕上，**在微软文档里没有明确说明**，官方示例都是针对顶层窗口的。

下一步可试的方向（都需要能看见屏幕的人配合判断，因为自动检测不可用）：

1. **换成顶层窗口**：不用 Progman 子窗口，而是创建一个顶层窗口并置于 z 序底部
   （传统 WorkerW 做法的变体）。本机的经典 WorkerW 路径不存在（那 50 个 WorkerW
   都是 173x34 的不可见遗留窗口），但"顶层窗口 + 置底"本身仍可试。
2. **`DCompositionCreateDevice2/3`**：Wallpaper Engine 能在这个位置画出来，可能用了
   不同版本的合成设备或 `IDCompositionDesktopDevice`。
3. **`--no-redirection` 开关**已经就绪，可以直接对比"带与不带"这个标志的差别。

`--test-desktop-layer` 与 `--play-video` 都能用，因此一旦有人能确认显示效果，
排查可以立刻继续。

### M4 验证手段的教训：不可重复的检测不能当判据

为了让"内容到底上屏了没有"这件事不依赖人工，我试了三种自动检测，**前两种都不可靠**：

| 手段 | 结果 |
| ---- | ---- |
| GDI `BitBlt` 抓屏 | **看不到** DComp 内容（Progman 带 `WS_EX_NOREDIRECTIONBITMAP`，没有重定向位图） |
| DXGI 桌面复制取色 | **结果不可重复**：同一个自检，一次采到 `#FF00FF`、下一次采到 `#000000` |
| `CreateTargetForHwnd`/`Commit` 返回值 | 只能证明"调用被接受"，不能证明"像素真的上屏" |

桌面复制在**对照实验**里给出过一次很有价值的结论：普通顶层窗口 + DComp 能被看到
（`#FF00FF`），而 Progman 子窗口看不到。但重跑时连"已知可见"的顶层窗口都变成黑色，
说明它的帧时序不确定。**因此它不能作为判据**——一个有时说 A、有时说 B 的检测，
无论哪次结果都不该采信。

于是改用**确定性**的验证方式：`--test-desktop-layer` 现在显示一张**自检图案**，
让人眼一秒判定：

- 四角各一个纯色方块：左上青、右上黄、左下绿、右下洋红；
  只看到其中一部分就说明窗口没铺满或位置偏了；
- 中间一条深灰横带，横带里用**白色方块的数量**表示这是第几块屏；
- 其余是接近黑的深灰，避免被误认为"这就是我的壁纸"。

为什么不用纯色：纯色无法回答"合成生效了没有"——用户看到屏幕变色时，
无法区分"我们的内容上屏了"和"壁纸本身就是这个色"。

图案生成器有单元测试盯着（四角颜色必须互不相同且都不是底色、编号方块数随序号增加），
因此"图案本身画对了"这件事是可自动验证的；只有"图案是否真的出现在屏幕上"
需要人眼确认。

**顺带修正一处我写错的东西**：调色板的颜色标注。`COLORREF` 是 `0x00BBGGRR`，
所以 `0x00D14700` 是**红**（B=00 G=47 R=D1）而不是我原先写的"蓝"，
`0x00006EB4` 是**蓝**而不是"橙"。规则记在这里，免得再错。

### M4 像素上传路径（图片与视频共用）

`DesktopLayer::present_pixels(monitor, pixels, width, height)` 把一帧紧凑 BGRA 像素
显示到某块屏上。实现是"建 `D3D11_USAGE_DEFAULT` 纹理并带 `pSysMem` 上传 →
`CopyResource` 到 `BeginDraw` 拿到的表面"。

**静态图片壁纸与视频帧走的是同一条路**：图片文件解码成 BGRA 后同样调它。
因此这一步同时为"图片壁纸"和"视频壁纸"打通了上屏能力。

尺寸不一致时（例如 1920x1080 的视频放到 4K 屏）在 CPU 上做最近邻缩放。
真正的裁切/缩放应该在 `image_prep` 阶段完成，这里只是保证"尺寸不匹配也能显示"。

### M4 顶层窗口模式（已实测，作为默认）

上一轮把"DComp 内容看不见"的疑点归到**子窗口**这条路上，这一轮实现了替代方案：
**自己建顶层窗口并压到 z 序底部**。传统 WorkerW 做法本质是同一思路，
只是它借用 Shell 已有的 WorkerW 窗口——本机那些都是 173x34 的不可见遗留窗口，
借不到，所以自己建。

实测（`--layer-mode top`）：

```
0x00B01602 pid=34624 "…\\.\DISPLAY1" (0,0) 2560x1440 可见=True
0x00700F38 pid=34624 "…\\.\DISPLAY2" (-1440,-93) 1440x2560 可见=True
位置核对: 每块屏的窗口都落在自己的显示器矩形上
退出后残留: 0
```

z 序（`EnumWindows` 从上到下，z# 越小越靠上）：

```
z#26   Shell_TrayWnd                     (任务栏)
z#390  WindowsWallPaperDesktopLayer      <== 我们的窗口
z#391  WindowsWallPaperDesktopLayer      <== 我们的窗口
z#392  Progman            (桌面图标层，最底)
```

即**我们在 Progman 正上方、所有普通窗口之下**，正是"图标层之下、桌面底层"的位置。
而且这是**真正的顶层窗口**（枚举得到、`FindWindow` 找得到），
会经过 DWM 的窗口重定向合成——而对照实验证明顶层窗口的 DComp 内容**能被看到**。

于是两种形态的差别是**合成路径不同**，不是风格偏好：

| 形态 | 位置与 z 序 | 是否经过 DWM 重定向合成 | DComp 内容可见性 |
| --- | --- | --- | --- |
| `child` | 正确（Progman 子窗口） | 否（由 Progman 自己绘制） | 未被任何自动手段看到 |
| `toplevel` | 正确（Progman 正上方） | **是** | 对照实验证明顶层窗口可见 |

**因此默认改为 `toplevel`**（`settings.toml` 里的 `layer_mode`，默认 `toplevel`）。
保留 `child` 作为对比与回退，命令行开关是 `--layer-mode child|top`。

> 说明：把默认改成 `toplevel` 的依据是**它符合"内容要经过 DWM 合成"这个已知条件**，
> 而不是"已经看到画面了"。`child` 那种形态下的内容直到今天也没有被任何手段看到过，
> 所以它不具备"更可能工作"的理由。

### M4 引擎的视频路由（已跑通）

上一步让视频进了图库，立刻引出一个问题：**引擎原本假定所有条目都是图片**，
于是会把 MP4 交给 `image` crate 解码——那永远失败，表现成
"反复选中同一个文件、反复失败"。所以路由不是锦上添花，而是上一步的必要收尾。

#### 做法：把视频呈现抽成 trait，保住引擎的可无头测试性

`wwp-core` 里有一半以上的测试是**无头**的（不碰桌面、不碰窗口）。
一旦引擎直接依赖 `desktop_layer`（要建窗口、要有显示器、要有 D3D 设备），
那些测试就没法跑了。因此加了一个只有两个方法的 trait：

```rust
pub trait VideoPresenter: Send + Sync {
    fn play(&self, monitor: &str, file: &Path) -> Result<(), String>;
    fn stop(&self, monitor: &str) -> Result<(), String>;
}
```

- 引擎侧：`DesktopSink::apply` **先按扩展名分流**，视频走这个 trait；
- 测试侧：一个记录调用的假实现，于是"路由"这件事能在无头环境下被完整验证；
- 运行时：shell 侧的 `VideoHostPresenter` 把它接到真实的 `DesktopLayer`。

5 条路由测试（全部无头）覆盖：视频被分流到呈现器、从视频切回图片时**先停视频**、
呈现器失败被如实报出、不存在的屏在调用呈现器之前就被拒绝、
没有桌面层时给出明确错误而不是假装成功。

#### "桌面层尚未启动"——一个只有跑真实流程才能发现的 bug

第一次跑混合图库实测时，视频全部失败，错误是"桌面层尚未启动"——
**尽管日志里刚说过"视频呈现已就绪"**。

原因：`PlaybackManager::start()` 的第一件事是 `self.stop()` 来停掉上一次运行，
而 `stop()` 会清空视频槽位。于是"先交桌面层、再启动轮播"这个很自然的顺序
会把刚交进来的桌面层立刻清掉。

**这个 bug 单元测试发现不了**：测试用假呈现器，不经过槽位。
修法不是调整调用顺序（那只是掩盖耦合），而是把两个职责分开：
`stop()` = 停视频 + `stop_core()`，`start()` 只调 `stop_core()`。
这样顺序不再影响结果。

这条经验值得记下来：**假实现让"逻辑"可测，但"真实组件的生命周期"
只有在真实流程里才暴露。** 两类测试都需要。

#### 端到端实测（真实引擎 + 真实桌面层 + 混合图库）

图库：6 张图 + 2 个视频，间隔压到 3 秒以便两条分支都被走到。

```
\\.\DISPLAY1 开始播放视频 landscape.mp4（目标尺寸 3840x2160）
\\.\DISPLAY1 换了 9 次，当前 landscape.mp4  ← 视频（走桌面层合成）
\\.\DISPLAY2 换了 9 次，当前 portrait.mp4   ← 视频（走桌面层合成）
轮播结束，已还原 2 块屏的壁纸
```

图片条目走 `IDesktopWallpaper`、视频条目走桌面层合成，两条路径都真实走到了，
没有出现"换纸失败"。

### M4 视频接入图库（上一轮补上的缺口）

**这是一个真实缺口，而且是本轮盘点时才发现的**：视频壁纸在之前几轮里只存在于
CLI 实验（`--play-video`），**扫描器根本不认视频文件**——`is_candidate_extension("mp4")`
返回 false，视频在遍历阶段就被当成"扩展名不符"跳过。而设计需求明确要求
"图库里混有 MP4/AVI 时按其顺序播放"。功能在，但**从未接入产品**。

补上的部分：

1. **`video_size` 模块**：从容器头读视频尺寸，**不依赖 Media Foundation**。
   理由：扫描 5 万个文件时，每个都建 Source Reader（协商解码器、可能初始化解码器）
   比读图片头贵几个数量级；而扫描只需要宽高，它就写在容器头里。
   这也让扫描不必把解码器全加载起来。

   - **MP4/MOV/M4V**：尺寸在 `moov > trak > tkhd`。要处理 64 位 box 长度、
     长度为 0（延伸到末尾）、`tkhd` version 0/1 的布局差异，以及**旋转**——
     手机竖拍的 MP4 用矩阵表示旋转，容器里宽高是横的，显示时要对调，
     不处理会让竖屏视频被判成横屏、筛选条件选错。
   - **AVI**：尺寸在 `strf` 的 `BITMAPINFOHEADER`。用 `biSize == 40` 区分视频流与
     音频流——音频的 `strf` 是 `WAVEFORMATEX`，头几个字节也像数字，不加这个判断
     会读出荒谬的"尺寸"。
   - MKV/WebM 不解析（EBML 变长整数复杂得多），走兜底。

   **解析失败时给 1920x1080 而不是 0x0**：0x0 的条目会被"最小宽度"之类的筛选条件
   全部排除，表现成"视频一个都播不了"；给一个常见分辨率只是筛选不精确，
   用户还能看到并播放它们。

2. **索引新增 `kind` 字段**（`image`/`video`），带 `#[serde(default)]` 让旧索引
   能读进来——旧索引里本来只有图片，默认成图片是正确的迁移语义。

3. **`IndexStats` 新增 `videos` 计数**，它是 `playable` 的**子集**
   （视频也是可播放条目，只是播放路径不同）。

端到端实测（6 张图 + 2 个视频的混合图库）：

```
扫描完成：候选 8，可播放 8，不支持 0，读不了 0，复用 0，探测 8
扩展名不符图片 : 0     ← 视频不再被当成"不符"
方向分布       : 横 4 / 竖 3    ← 视频尺寸参与了统计
```

索引内容（视频尺寸与 ffprobe 的答案一致）：

```
landscape.mp4 : 1920x1080 kind=video fmt=mp4 ok=1
portrait.mp4  :  720x1280 kind=video fmt=mp4 ok=1
square.jpg    : 1000x1000 kind=image
```

#### 接入时按契约变化更新的测试

两个测试断言的正是**旧契约**，因此改的是测试而不是代码：
- `probe::tests::extension_classification_matches_the_two_tables` 里
  `assert!(!is_candidate_extension("mp4"))` → 改为断言视频**必须**进候选；
- `scan::tests::scan_finds_images_and_ignores_non_images` 原本断言"只应有两张图、
  两个非图片被忽略" → 改为"两张图 + 一个视频、只有 .txt 被忽略"，
  并补上"损坏的 mp4 也要有兜底尺寸"的断言。

改测试是危险的，因此这两处都在注释里写明了"原先断言的是什么、为什么改成这样"，
避免以后有人以为测试是被迁就代码而改的。

## 4. 崩溃恢复与长时稳定性（M5）

### M5 崩溃后的壁纸恢复（A1，已实测）

> **【2026-02 已作废】** 下面这一节（"崩溃后自动恢复壁纸"）描述的机制
> **已被整体删除**：用户明确要求程序永远不还原他的壁纸，因此快照文件、
> 启动恢复、`--test-simulate-crash` / `--test-startup-recovery` 两个入口
> 一起删掉了。这段保留下来只作为当年排查过程的记录——里面关于
> "什么时候快照是可信的""先还原再删快照"的推理依然是对的，
> 只是已经不再有代码实现它。
#### 缺口：快照只写下来，从来没用来自动恢复

原先的处理是：开始轮播前拍一份壁纸快照写到 `data/wallpaper-snapshot.json`，
停止时按它还原并删除快照。注释里写着"即使程序被强制结束，用户也能据此
**手工**恢复"。

也就是说：如果程序崩溃、被任务管理器结束、断电、注销——用户的壁纸就停在
我们设的那张图上，而他得自己去打开一个 JSON、看懂它、再手动设回壁纸。
**那不是恢复，那是把问题留给用户。** 而"壁纸被改了回不去"恰恰是这类程序
最不能接受的失败。

#### 做法：启动时发现残留快照就自动还原

```text
快照存在  ⇔  上次没有正常收尾  ⇔  现在需要还原
```

这个等价关系让实现与"具体是崩溃、断电还是注销"无关——
只要快照还在，就必须还原。因此它一次覆盖了恢复矩阵里的多种情况。

几个刻意的决定：

- **只在成功还原之后才删除快照**。部分屏还原失败、或整体失败时保留快照，
  下次启动会再试一次。反过来（先删再试）会让没还原成功的屏永远回不去。
- **损坏的快照要删掉**，否则每次启动都会尝试解析同一份坏文件。
- **必须在任何新的壁纸操作之前执行**，也就是在主窗口创建之前。
  顺序反了的话我们会先拍一张"脏"快照——把我们自己设的图当成用户的原状——
  那张错快照之后就再也修不回来了。
- **只读诊断入口（`--diagnose`、`--probe-*`、`--dump-frame` 等）不触发恢复**：
  它们是只读工具，不该在用户没打算启动程序时动桌面。
  `enters_window_mode()` 用"除已知只读入口之外都算窗口模式"的写法——
  反过来写（列出窗口模式的标志）会漏，而漏的后果是"诊断命令动了用户桌面"。

#### 实测

两步实验，把"崩溃"这件难以故意制造的事变成可复现的流程：

```powershell
# 第 1 步：模拟崩溃前一刻（拍快照 → 换壁纸 → 不还原就退出）
.\WindowsWallPaper.exe --test-simulate-crash --dir <图库>

# 第 2 步：验证恢复
.\WindowsWallPaper.exe --test-startup-recovery
```

结果：

```
发现残留的壁纸快照，说明上次退出时没来得及还原；现在自动还原
已按快照还原 2 块屏的壁纸
恢复前的壁纸：...mild_16_10.jpg                                    ← 崩溃时留下的
尝试还原 2 块屏：...WallpaperEngineOverride_randomLHVFFU.jpg（成功）← 用户的原状
恢复后的壁纸：...WallpaperEngineOverride_randomLHVFFU.jpg
快照文件现在存在：false
```

再用**真实用户路径**（直接双击、不带参数启动）确认了一遍：

```
发现残留的壁纸快照，说明上次退出时没来得及还原；现在自动还原
已按快照还原 2 块屏的壁纸
主窗口已创建        ← 恢复发生在窗口之前
托盘已就绪
```

边界情况也验证了：没有残留快照时静默通过；快照文件损坏时报警、删除、
继续启动（不会卡在一个坏文件上）。

#### 一个仍未解决的观察 → 已解决：是回读延迟，不是第三方改写

上一轮观察到"同一对操作（`SetWallpaper` 后立刻 `GetWallpaper`）给出不一致的结果"，
当时猜测是 Wallpaper Engine 的覆盖层在改写壁纸。

**这个猜测是错的。** 用一条专门的对照实验（`--test-wallpaper-readback`）
把两种可能分开了——设置壁纸后分三次回读：

```
原状：...WallpaperEngineOverride_randomLHVFFU.jpg
已设置壁纸：tmp\mixlib\square.jpg

回读（立刻）  → WallpaperEngineOverride_randomLHVFFU.jpg   ← 旧值
回读（等 3 秒）→ square.jpg                                 ← 新值
回读（再等 5 秒）→ square.jpg                               ← 稳定，没有被改回
```

结论：**`SetWallpaper` 之后立刻 `GetWallpaper` 会返回旧值**——
Windows 需要先把图片转码成 `TranscodedWallpaper` 并让桌面重绘。
与 Wallpaper Engine 无关（它的覆盖文件最后写入时间是两天前，并没有在改写）。

这解释了此前反复出现的"上屏无法自证"：我一直在用"设置后立刻回读"
或"立刻截屏"来验证，而那两种判据在换纸刚发生的那一小段时间里都是不可靠的。

#### 换纸耗时的说法被纠正了

项目里一直写着"每次换纸 48~71 ms"。用 `--test-wallpaper-latency` 一测，
发现那个数字的含义被误解了：

| 指标 | 红色轮 | 蓝色轮 |
|---|---|---|
| API 调用返回 | 7 ms | 9 ms |
| 回读变为新路径 | 226 ms | 230 ms |
| 屏幕像素变为新主色 | 12 秒内未变 | 12 秒内未变 |

- "48~71 ms"是**管理器记录的时间**（含准备位图），而 API 调用本身只要 7~9 ms；
- 但**回读**要到约 **230 ms** 才变成新路径——也就是说"画面真的换过去"
  比那个数字晚一个数量级；
- 截屏判据仍然失效（GDI 看不到壁纸重绘，与此前"桌面复制/GDI 都看不到
  DComp 内容"是同一类限制），因此**可见延迟的精确值仍未测得**。

诚实的结论：**"换纸耗时"只能说明 API 调用完成，不能说明用户已经看到新图。**
界面与日志里那个数字不该被理解成"用户等待的时间"。精确的可见延迟
需要一个可靠的画面判据，而目前没有。

#### 恢复矩阵：显示器变化过的三种情况（已实测）

崩溃期间用户可能拔掉外接屏、换接口插、或切换投影模式，因此快照里的设备路径
**不一定还对得上**。这里有一个必须知道的事实：

> **给一个不存在的设备路径调 `SetWallpaper` 也会返回成功。**

也就是说，如果照着快照里的旧路径直接设，程序会报"还原成功"而实际上什么都没发生。
这比报错更糟——用户以为壁纸回来了。

因此新增 `restore_matched`，比 `restore` 多做两件事：

1. **匹配**：把快照里的记录与当前枚举出的屏对上。先按设备路径，
   路径对不上时退回按**屏幕矩形**——屏幕位置比设备路径稳定
   （路径里含连接序号与 UID，换个接口插就可能变，而分辨率与坐标通常不变）。
2. **如实报告**：对不上的记录标成失败并说明"这块屏现在不在"。

三种情况的实测（用 JSON 精确伪造快照，而不是文本替换——见下面的教训）：

| 情况 | 快照里的路径 | 快照里的矩形 | 结果 |
|---|---|---|---|
| 屏还在，路径也没变 | 匹配 | 匹配 | 按路径匹配上，**成功** |
| 换了接口，路径变了 | 对不上 | 匹配 | **按矩形匹配上，成功**；报告里给出实际用到的设备路径 |
| 拔掉了，路径与位置都对不上 | 对不上 | 对不上 | **失败**，说明"这块屏现在不在"；**快照保留**以便接回来后重试 |

后两种情况都**不删除快照**——只有全部成功才删。否则用户唯一能回去的依据就没了。

#### 一个方法上的教训：验数据要先把它打出来

测"拔掉外接屏"时，我头两次都用文本正则去改快照里的矩形，而**替换静默失败了**
（矩形没变），于是被测数据其实一直与真屏匹配——还原当然成功，
而我却把它读成"程序没有如实报告失败"，差点去改一个本来正确的实现。

根因是：`ConvertTo-Json` 写出来的数组是**多行**格式，我用单行正则去匹配自然不中；
而且我没有检查"伪造到底生效了没有"。

两处修正：伪造改用 `ConvertFrom-Json`/`ConvertTo-Json` 做真正的结构化编辑；
测试入口（`--test-startup-recovery`）**先把读到的快照内容打印出来**。
不加这个打印，验证过程就只能靠猜"它到底加载了什么"。

#### 恢复矩阵的匹配逻辑现在有单元测试了

`restore_matched` 的匹配规则原本内联在函数里，只能靠真机拔插显示器来验证。
抽成纯函数 `match_saved_monitor` 之后，所有分支都能在**无头环境**覆盖：

| 测试 | 守的是什么 |
|---|---|
| 屏还在、路径没变 | 按路径匹配（最常见的情况） |
| 路径大小写不同 | 大小写不敏感比较；不做的话用户会看到毫无道理的"这块屏现在不在" |
| 换接口、路径变了 | 按矩形匹配上，且匹配到**位置相同的那块**而不是第一块 |
| 拔掉了、路径与位置都不对 | **返回 `None`**——绝不能退化成"随便找一块屏" |
| 快照没有矩形信息 | 只能靠路径；不能因为"两边都没有矩形"就把第一块当成目标 |
| 一边有矩形一边没有 | `Some(rect)` 不等于 `None` |
| 当前一块屏都没有 | 不 panic、不凭空匹配 |

其中"拔掉了"那条是最重要的：如果实现退化成"随便找一块屏设上去"，
就会把**另一块屏**的壁纸覆盖掉——那比"不还原"更糟，
因为用户什么都没做，壁纸却被改了。

**为什么值得为这几行逻辑写测试**：真机测试没法穷举"路径变了但位置没变"
"位置变了但路径没变"这些组合，而把壁纸设到错误的屏上是用户很难自己诊断的问题。

#### 恢复矩阵：目前验证到了哪一步

区分"实测过"与"仅代码上处理了"很重要——列表里混着两者会让人误以为全都验过。

| 场景 | 状态 | 怎么验的 |
|---|---|---|
| 正常停止轮播 | **实测** | 托盘/界面停轮播，壁纸还原 |
| 崩溃/被任务管理器结束 | **实测** | `--test-simulate-crash` + `--test-startup-recovery` |
| 真实用户路径启动（不带参数） | **实测** | 造残留快照后直接启动，日志确认恢复发生在主窗口之前 |
| 快照里的图片文件已不存在 | **实测** | 伪造快照指向不存在的文件：报失败、**保留快照** |
| 显示器拔掉（路径与位置都不对） | **实测** | JSON 精确伪造：报"这块屏现在不在"、保留快照 |
| 显示器换接口（路径变、位置不变） | **实测** | JSON 精确伪造：按矩形匹配成功，报告实际用到的设备路径 |
| 快照文件损坏 | **实测** | 写入非法 JSON：报警、删除、继续启动 |
| 没有残留快照 | **实测** | 静默通过 |
| 还原过程中再次崩溃 | **未实测** | 代码上可行（快照在全部成功前不删），但没有故意制造过 |
| 断电（写快照时断电，文件写了一半） | **未实测** | 走"快照损坏"那条分支，但断电本身没法在本机构造 |
| 显示器分辨率变化后再还原 | **未实测** | 位置变了会让矩形也匹配不上，会走"这块屏现在不在" |

最后三条是**如实列出**的未验证项——它们不影响"本机基线可用"这个目标，
但如果将来要宣称"任何情况下都能恢复"，这三条得先补上。

#### 便携路径与只读回退（M1 验收项，实测）

| `WWP_HOME` | 结果 |
|---|---|
| `Z:\`（不存在的磁盘） | 回退到程序目录，**不崩溃**，如实报告来源 |
| 可写目录 | `来源: env-override`，创建 `config/ data/ logs/ webview2/ wwp-data-location.txt` |
| 未设置 | 用程序目录（便携模式），`来源: dev-project-dir`（开发时） |

`wwp-data-location.txt` 的内容是一条可直接读懂的说明，包含数据根目录、
来源、程序目录，以及"把整个文件夹拷到别处后如何确认是便携模式"。
把程序文件夹拷走后，这个标记文件的存在本身就是"数据确实在程序目录"的证据。

### M5 长时稳定性（实测 5 分钟 + 6 分钟，20 分钟进行中）

用 `--test-ui-playback-path` 长跑，**从外部采样**进程的内存与句柄——
自己报自己不可靠，真实持有者（操作系统）才是可靠来源。

#### 混合图库（含视频）跑 5 分钟

| 指标 | 谷底（反复出现） | 峰值（反复出现） |
|---|---|---|
| 内存 | 88–101 MB | 176–283 MB |
| 句柄 | 700–707 | 844–918 |

数据是**锯齿形**：视频播放会建 D3D 设备、解码线程、音频线程，
切走后释放。**谷底稳定**（88 → 101 MB），**没有单调上升趋势**。
共换纸约 142 次、视频播放 20 次、**0 警告 0 错误**。

#### 纯图片跑 6 分钟（用来把视频资源的影响排除掉）

| 时间 | 内存 | 句柄 |
|---|---|---|
| 20–240 秒 | 46.0–46.9 MB（**完全平稳**） | 529–535 |
| 260–360 秒 | 52.5–52.8 MB（另一次平稳） | 568–573 |

共 **242 次换纸、0 视频、0 警告**。位图缓存命中正常
（日志里是"命中缓存，未重新解码"）。

260 秒处出现**一次台阶**（约 +6 MB、+40 句柄），之后再次完全平稳。
台阶而不是斜坡这一点很重要：**泄漏会表现为持续上升，而台阶说明
"某个资源被分配了一次"**。第 5 分钟起温度稳定在 52.5–52.8 MB 达 100 秒不动。

结论：**在两个时间尺度上都没有观察到泄漏。** 但 6 分钟不足以证明长期稳定，
因此又开了 20 分钟的长跑（结果见下一节或环境日志）。

#### 20 分钟长跑（纯图片，间隔 3 秒）

40 个采样点（每 30 秒一次，共 1171 秒）：

| 指标 | 全程 | 后 12 分钟（第 8–20 分钟） |
|---|---|---|
| 内存 | 45.8 → 53.1 MB（跨度 7.3 MB） | **52.7 ~ 53.1 MB（跨度 0.4 MB）** |
| 句柄 | 533 ~ 575 | 567 ~ 575（无上升趋势） |

关键对比：这次后期稳定在 **52.7–53.1 MB / 567–575 句柄**，
而 6 分钟那次后期稳定在 **52.5–52.8 MB / 568–573 句柄**——
**两次独立运行落在同一区间**，说明那点增长是"启动后建立稳态"，
不是持续泄漏。如果存在泄漏，两次运行的不同时长应当给出明显不同的终值。

#### 结论与诚实的边界

在这次测量的时间尺度（5 分钟混合图库、6 分钟与 20 分钟纯图片）上，
**没有观察到内存或句柄泄漏**。混合图库那次的锯齿形波动是视频资源的
正常分配/释放（D3D 设备、解码线程、音频线程），谷底稳定。

**但这不等于"8 小时无泄漏"**。已测的最长时间是 20 分钟，
而缓慢泄漏（例如每 10 分钟 1 MB）在这个尺度上无法与稳态噪声分开。
目标里的 8 小时长跑还没有做。

#### 一个连带发现的粗糙处

第 20 分钟长跑结束后，我按惯例去读 `logs/app.log` 统计换纸次数，
发现**该文件不存在**——因为紧接着上一次测试我设置过 `WWP_HOME`
指向另一个目录，而日志写到了那边。

这不是产品缺陷（日志确实写在了当时的数据根目录），但提示一件事：
**测试脚本按固定路径读日志会在切换数据根之后失效**，
统计结果会静默变成 0 而不是报错。后续统计应当从数据根推导日志路径。

### M5 打磨与压力测试

已完成的部分（提前做了，因为不影响桌面、可以安全验证）：

- **托盘常驻**（设计规格 D5 只要求这一项）：显示主界面、开始/暂停轮播、换一张、退出。
  关闭窗口 = 隐藏到托盘（壁纸软件里关闭设置界面不等于退出），因此托盘菜单里必须有
  明确的"退出"入口，且退出顺序是**先停轮播（按快照还原壁纸）再退出**——
  反过来会把改动后的壁纸留在用户桌面上。
  `minimize_to_tray = false` 时关闭窗口就是退出，此时同样会先还原壁纸。
- **显示器热插拔自动适配**：隐藏的顶层消息窗口监听 `WM_DISPLAYCHANGE`。
  收到变化且正在轮播时，按新的显示器列表**重建每屏计划**——拔掉的屏不该继续被换纸，
  新插的屏必须被纳入播放。未轮播时只记日志（下次启动自然会用新列表）。
- 实测（`--broadcast-display-change` 脚本模拟广播）：
  ```
  收到显示器变化广播（新分辨率 3840x2160）
  显示器配置已变化（当前未轮播，无需适配）
  ```
  隐藏消息窗口确实收到了广播，处理器也确实跑了。
  **说明**：模拟广播只能证明"广播能收到、处理器会跑"，不能替代真实拔插
  （真实拔插会改变显示器枚举结果，模拟不会）。真实拔插留作人工验证。

**顺带修掉一个会导致丢失用户壁纸的缺陷**：`start()` 原本每次都会重新拍壁纸快照。
但"重启轮播"是常见操作（改设置、显示器热插拔），第二次拍到的快照记录的已经是
**我们自己设的图**；用户点停止时就会把我们设的图"还原"回去，他原来的壁纸再也找不回来。
现在改为：**只要上一次轮播留下的快照还在就沿用它**，只有第一次接管桌面时才拍新的；
界面点"停止并还原壁纸"之后快照会被删除（此时它已失效，留着会让下次启动沿用过期的"原状"）。

## 5. 测试稳定性核查

### 测试稳定性核查

有一轮连续跑全量测试时出现过**一次失败，但当时没有保留输出**，之后无法复现。
处理方式与结论：

- 先排查所有**基于耗时/时序的断言**——这是最容易偶发的一类。
  全项目只找到一处（`scan::tests::second_scan_reuses_unchanged_entries` 里
  "二次扫描不应明显更慢"的比例断言），已改成小耗费用绝对余量、大耗时才比比例。
  其余涉及 `Duration` 的断言都是**纯函数比较**（`is_probably_smooth(30.0, 10ms)`），
  与真实时间无关，不会偶发。
- 确认测试目标完整：`cargo test --workspace` 覆盖 3 个目标
  （主程序 5 项、`wwp-core` 119 项、doc-tests 0 项），我的检查脚本没有漏掉某一组。
- 之后**连跑 32 次全部通过**（含 12 次只跑扫描测试、15 次落盘留存输出）。

**如实记录**：那一次失败的输出没有被保留，因此**它的原因至今未知**。
它没有复现，但这不等于它不真实——只能说在当前的执行环境下没有再出现。
后续如果再遇到，第一件事是把完整输出落盘（现在压测脚本已经这么做）。

## 8. 未解决的环境异常（§14）

> **这条至今没有解决。** 结论是「环境相关的渲染问题，不是本项目的布局 bug」，
> 当前处置是把初始窗口开到 1400x950 以容纳偏大的内容。
> 留在这里是因为它是一条**悬而未决的线索**，不是已归档的历史。

### 环境问题记录（M2 实测中发现，尚未解决）

**WebView2 的设备像素比在本机被算大了。** 实测数据（开发机 Win11 24H2 build 26100.1000，双屏 2560x1440 + 1440x2560，主屏 150% 缩放）：

| 量 | 实测值 | 预期值 |
|---|---|---|
| 窗口客户区（`GetClientRect`） | 1200 x 800 物理 px | — |
| 窗口 DPI（`GetDpiForWindow`） | 144（150%） | 144 |
| 页面 `window.devicePixelRatio` | **1.875** | 1.5 |
| 页面 `innerWidth/innerHeight` | 961 x 641 CSS px | 800 x 533 |
| Tauri `inner_size()` | 1800 x 1200 物理 px | 1200 x 800 |

两个独立的现象：
1. `devicePixelRatio` = 1.875 = 1.5 × 1.25，多出 25%，因此页面内容比预期大约 25%。
2. Tauri 的 `inner_size()` 比 `GetClientRect` 大 1.5 倍（1800 vs 1200），即它报告的不是物理尺寸。

**已排除的原因**（都做过对照实验，结论一致）：
- 不是 `windowEffects`（去掉 mica 后数值不变）；
- 不是陈旧的 WebView2 profile（删掉 `webview2/` 目录重建后数值不变）；
- 不是窗口尺寸设置方式（改配置初始尺寸、运行时 `SetWindowPos`，结果一致）。

**影响与临时处置**：界面可用，但内容偏大 25%，窗口开小了会裁到右侧。当前把初始窗口开到 1400x950 以容纳。这不是正确的修法，只是让界面在本机完整可见。

**排查方向**（留给后续）：
- 本机装有两个第三方虚拟显示适配器，且两块屏 DPI 不同。WebView2 在混合 DPI + 虚拟适配器环境下的 monitor-scale 检测是有已知问题的（参考 [WebView2Feedback #4826](https://github.com/MicrosoftEdge/WebView2Feedback/issues/4826) 与 `CoreWebView2Controller.ShouldDetectMonitorScaleChanges`）。
- 可尝试的修法：显式控制 `ShouldDetectMonitorScaleChanges`（Tauri 未暴露，可能需要在 `WebviewWindowBuilder` 之后取到 controller）；或按实测比值纠正页面缩放（但这是掩盖而不是修复）。
- 结论：**这是一个环境相关的渲染问题，不是本项目的布局 bug**。判断依据是布局本身正确（CSS 视口与客户区按同一比值换算后一致），出问题的只有缩放比。

## 9. 「程序会不会自己退出」（2026-10-16 取证）

> 用户 2026-10-16 报："我总是感觉现在的程序会自己退出，有时候我明明没有退出程序，
> 但是托盘就是看不到程序图标了，并且壁纸也停止了轮播，而是停留在了某一张。"
> 他要求**先只分析、不要跑本地测试**。
>
> 结论：**已排除"程序自己退出"**——用户那一份的 17 段日志**没有一段是正常退出**，
> 而每一段都精确终止于一次 Windows 关机/重启。下面把取证方法与判据留下来，
> 因为"程序是不是还活着"这类问题以后还会再遇到，而它有一套固定的看法。

### 9.1 先看用户机器上的真实证据（只读，不改任何东西）

| 检查项 | 位置 | 结果 |
|---|---|---|
| 崩溃报告 | `logs/crash/` | **空**（Rust panic 一定会在这里留一份，见 `install_panic_hook`） |
| 应用日志里的错误 | `logs/app*.log` 里的 `[ERROR]` | 只有一条"显示器枚举结果与系统壁纸接口不一致"，与退出无关 |
| Windows 错误报告 | `%ProgramData%` / `%LOCALAPPDATA%` 的 `WER\ReportArchive` | **没有本程序的任何报告** |
| 应用程序错误/挂起事件 | `Application` 日志里的 `Application Error` / `Application Hang`（近 20 天） | **没有一条属于本程序**（同期 Photoshop / Acrobat / Explorer 都在崩，说明这张表是灵的） |
| 程序是否被挂起/冻结 | `app.log` 里每 2 秒一行的轮询（前端 `useScanWatcher` 的节奏）有没有断档 | 整段连续；**唯一的空档正好是那次重启的 92 秒** |
| 每次启动的时刻 | `启动 WindowsWallPaper：…` 那一行 | 与 `System` 日志的 `6005`（事件日志服务启动 = 系统开机）**逐次对齐，误差 0~2 分钟** |
| 每段日志的结尾 | 每份 `app*.log` 的最后一行 | **永远是一行 DEBUG 轮询，从不出现"正常退出"** |

由此得到两个互相印证的判断：

1. **程序没有崩、也没有被挂起**：崩溃会留下 `logs/crash/`，
   挂起会在 2 秒一行的轮询上留下空档，两者都没有。
2. **每一次"消失"都对应一次系统关机/重启**。那台机器 2026-10-11~10-16 这 6 天里
   重启/关机了 14 次（含 3 次"其他（计划外）"与 3 次 Windows 更新），
   而用户是在开机后才发现"托盘图标没了、壁纸停在某一张"——
   对他来说这就是"程序自己退出了"，但实际是**整个 Windows 结束了会话**。

### 9.2 为什么"正常退出"这四个字在日志里从来没出现过（这是一条真 bug，已修）

取证时发现一件更要紧的事：**1.13.1 及更早的版本里，
`log::info!("正常退出")` 是一行永远执行不到的死代码。**

原因是 Tauri 的两种退出方式都走 `std::process::exit`（不展开栈）：

```
Builder::run()          →  tauri 在事件循环结束后自己 std::process::exit
AppHandle::exit(0)      →  tauri 的 App::exit 直接 cleanup_before_exit() + std::process::exit
```

而那一行原本写在 `run()` **返回之后**。于是：

- 托盘菜单点「退出」→ `app.exit(0)` → 进程立刻结束 → 那行不打印；
- 被任务管理器结束 / 关机 / 注销 → 进程被拆掉 → 那行不打印。

**两种情况的日志一模一样**，这就是为什么这件事只能靠"关机时间对齐"来推，
而不能直接看日志。这是 §7.2「两套机制只有一半能工作」的同一类毛病：
**看着有日志，其实那行不可能被打印。**

**修法（1.14.0）**：改用 `App::run_return` + `RunEvent::Exit` 回调。
`RunEvent::Exit` 是**所有**退出路径的汇合点（tauri 先跑 `cleanup_before_exit`，
再回调这里，最后才 `std::process::exit`），因此在那里记一行就覆盖了全部路径：

```
事件循环结束，进程正常退出（本行缺失即代表进程被外力结束）
```

从此**"程序是被强杀的"有了可判据**：
日志里有这一行 = 走的是正常退出；没有 = 进程被外力结束（关机 / 注销 / 任务管理器 / 崩溃）。

> 顺带：不要把这件事做成"托盘退出前先记一行"——那只覆盖托盘那一条路，
> 而关闭窗口直接退出（设置里关掉了「最小化到托盘」）与将来任何新入口都会漏。
> 这与 §10.5「记录点只有一处才不会漏」是同一条经验。

### 9.3 托盘图标消失：候选原因与判据（按可能性排序）

**进程真的不在了**（上一条已经证明的那类）：

1. **Windows 关机 / 重启 / 注销 / 快速启动**——已由本机日志证实是主因。
2. **任务管理器"结束任务"、第三方"内存清理/开机加速"工具**——
   会把进程直接结束，日志只会在中途断掉；有了 §9.2 的那一行就能与正常退出区分。
3. **被终止时正在换纸/写产物**——不会让进程退出，但会留下一个半截文件；
   下一次换纸会覆盖它（`image_prep::write_atomically` 走临时文件 + 改名）。

**进程还在，只是托盘图标不见了**——这一类同样符合用户描述的"看不到图标"：

4. **explorer.exe 重启 / 崩溃**。托盘图标由 taskbar 托管，taskbar 没了图标就没了。
   本机 `Application Error` 里 **explorer.exe 崩过 8 次以上**（近两个月），
   所以这条在用户机器上是真实存在的可能性。
   当前依赖 `tray-icon 0.25.1`，它**会**监听 `TaskbarCreated`
   广播并重新注册图标（`RegisterWindowMessageA("TaskbarCreated")` +
   `ChangeWindowMessageFilterEx`），因此这一条在新版依赖上应当自愈；
   但它只在"explorer 真的广播了"的情况下成立。
5. **Windows 11 的「任务栏设置 → 其他系统托盘图标」被关掉**，
   或图标被拖进溢出菜单（`^`）里藏起来了——这是"找不到图标"最常见的原因，
   与程序无关，**而用户看到的现象与"程序退出了"完全一样**。
6. **程序被 Windows 判定为挂起**（`Application Hang`）——本次取证里没有本程序的记录。

**看起来像退出、其实不是**：

7. **`pause_on_fullscreen = true`（用户当前是开的）**：某块屏上有程序全屏
   （含**最大化**窗口）时会自动暂停那块屏的轮播，退出全屏才恢复。
   表现是"壁纸停在某一张不动了"，而进程与托盘图标都好好的。
   日志判据：`检测到程序全屏，已自动暂停这块屏的轮播` 后面没有对应的
   `已退出全屏，恢复这块屏的轮播`。取证时统计过：551 暂停 / 544 恢复，
   差的 7 次都能被后面的会话解释掉，**不是长期挂着的状态**，
   因此这一条在本次不是主因，但它是最容易与"程序退出了"混淆的一条。
8. **设置里的「最小化到托盘」被关掉**（用户当前是开的 `true`，因此不是本次原因）：
   那种设置下**关闭窗口 = 退出**，进程真的会结束，只是用户以为只是关了窗口。

### 9.4 以后再遇到"程序自己退出了"，按这个顺序取证

```
① 任务管理器里还有没有 WindowsWallPaper.exe？
     有 → 是"托盘图标不见"这一类，看 §9.3 的 4/5/7 条
     没有 → 真的是进程没了，看 ②
② logs\app*.log 里搜「事件循环结束，进程正常退出」（1.14.0 起有这一行）
     有 → 是正常退出：谁点的退出？（托盘「退出」/ 关闭窗口 + 未开最小化到托盘）
     没有 → 被外力结束：查 System 日志的 1074（关机/重启）与
            Application 日志的 Application Error / Application Hang
③ logs\crash\ 里有没有新的 panic-*.txt
     有 → 是 Rust panic，报告里有位置与详情（release 是 panic=abort，会立刻结束进程）
④ 有没有断在 2 秒一行的轮询上、且当时既没关机也没崩溃？
     → 那种"静默中断"才是真正需要继续查的：先去加探针，不要猜
```

**一句话结论**：用户这台机器上，程序每一次"自己退出"都对应一次 Windows 关机/重启，
日志证据是完整的；而"托盘图标看不到"还有 explorer 重启与 Win11 图标设置两个
与程序无关的常见来源。1.14.0 起，正常退出会在日志里留下一行明确的记录，
下一次再遇到就能当场分辨是"谁结束的进程"。
