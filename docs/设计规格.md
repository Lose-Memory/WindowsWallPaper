## 1. 项目目标

Windows 桌面壁纸播放器：**每块显示器各自独立播放图片列表**。

需求来源是用户的原话（逐轮记录不随仓库发布）。逐条落点：

| # | 需求 | 现状 |
|---|---|---|
| 功能 1 | 万级图库流畅 | ✅ JSONL 索引按需加载；6444 张首次全量扫描 141 s |
| 功能 2 | 按需加载、不全部入内存 | ✅ 索引逐行读，只解码当前显示的那张 |
| 功能 3 | 随机 / 顺序 | ✅ `random`（带历史，避免短期重复）/ `sequential` / `sequential_reverse` |
| 功能 4 | 多屏不同列表 | ✅ **播放列表模型**：一个列表关联多个图库，每屏手动选当前列表 |
| 功能 5 | 按屏独立筛选 | ✅ 长宽比区间 + 最小尺寸，设在**显示器**上，所有列表共用 |
| 功能 6 | 视频壁纸 | ⏸ 代码已跑通但**默认关闭**，界面上不出现（见 §8） |
| 功能 7 | 音量 / 静音 | ⏸ 后端已就绪，随功能 6 一起启用 |
| 功能 8 | Win11 观感 | ✅ Mica + 圆角 |
| 功能 9 | 扫描子目录、落盘、按需加载 | ✅ 目录树可勾选层级，默认只展开第一层 |
| 功能 10 | **不移动、不修改原文件** | ✅ 图库全程只读，有 `--test-library-readonly` 守着 |

### 已确认的决策

| # | 决策项 | 结论 |
|---|---|---|
| D1 | UI 技术栈 | Tauri 2 + React 19 + TypeScript + Tailwind 4（对齐参考项目） |
| D4 | 数据存放 | 全部放**程序目录旁边**（便携式），不写系统目录 |
| D5 | 托盘 | 只做"托盘常驻"；**不做开机自启**。全局快捷键后来按需求加上了，共五个（NSFW 模式 / 暂停继续 / 下一张 / 上一张 / 显示主界面，见 §5"全局快捷键"） |
| D6 | 附加功能 | 要排除目录、要日志与崩溃报告落盘；**不要**切换过渡动画；不要多语言。**不要任何"还原壁纸"行为** |
| D8 | 依赖缓存 | 允许放在项目外（标准全局缓存），不做重定向 |
| D10 | 目标系统 | **只支持 Windows 11**；Mica 原生可用，不需要降级分支 |
| D11 | 静态多屏方案 | `IDesktopWallpaper` **逐屏设图**（见 §6 的对比） |
| D12 | 多屏模型 | 每屏一个独立"呈现单元"：独立列表、独立计时器、独立进度 |
| D13 | 参考对象 | 静态多屏参考 Lively Wallpaper；`ref/` 的 KokoroPaper 仅供引擎结构参考 |

**不在项目之外下载任何东西**（依赖缓存除外，见 D8）。
需要联网的东西一律先问用户——因此文件选择框用的是 Windows 自带的
`SHBrowseForFolderW`，而不是 `tauri-plugin-dialog`。

## 2. 核心抽象

**单进程，两半：**

```
外壳  src-tauri/src/                Tauri 窗口、托盘、日志、系统广播、命令路由
引擎  src-tauri/crates/wwp-core/    索引、扫描、筛选、选择器、壁纸设置、
                                   图像预处理、便携路径
```

**引擎不允许依赖 `tauri`**（有测试守着）。这条约束的理由：
`tauri` 依赖会让 156 项引擎测试全部需要图形环境，而它们现在是**无头**的、
可以随便跑。这是整个项目可测试性的基础。

前端与后端之间是 **一批独立命令**（`main.rs` 的 `generate_handler!` 是白名单），
不是单一入口。命令与命令行开关的清单见 `AGENTS.md` 第 5 节。

### 引擎模块（按实际存在的写）

| 模块 | 职责 |
|---|---|
| `paths.rs` | `app_root()`、可写性探测（真写一个探针文件）、回退到 `%LOCALAPPDATA%` |
| `config.rs` | `settings.toml` 的读写与默认值 |
| `library/scan.rs` | 目录遍历、扩展名与内容双判定、尺寸读取、并行探测、进度上报、可取消 |
| `library/index.rs` | `index.jsonl` 的增量读写、原子替换（temp + rename） |
| `library/exclude.rs` | 排除规则匹配（只有目录前缀一类，见 §"排除规则是前缀匹配"） |
| `library/probe.rs` | 只读图片头部判断尺寸，不解码整图 |
| `playback/mod.rs` | 每屏独立的播放循环与计时；两种"不轮播"（`single_image` 与空播放列表）在这里分出形态 |
| `playback/select.rs` | **只有随机**：最近 10 个名字不重复（顺序 / 倒序已被用户取消） |
| `wallpaper/mod.rs` | `IDesktopWallpaper` 逐屏设图（快照/还原只有 CLI 实测工具在用，程序本体不用） |
| `image_prep.rs` | 解码 / 按屏裁切 / 写出 BMP（每屏两个文件轮换覆盖，见 `AGENTS.md` §10.9） |
| `engine.rs` | 把设置解析成每屏计划 + `DesktopSink`（解码→落盘→调系统接口）；`bind_screens` 按屏幕**物理位置**从左到右排序 |
| `monitors.rs` | 屏幕枚举（`EnumDisplayMonitors` + `GetMonitorInfoW`） |
| `fullscreen.rs` | 全屏检测：枚举所有可见顶层窗口，按"最大化（且主要落在该屏）或覆盖率 ≥ 0.95"逐屏判定。判据是纯函数、可无头测试；**不依赖前台窗口**（见 `AGENTS.md` §10.28） |
| `hotkey.rs` | 快捷键字符串 → 修饰键 + 虚拟键码；五个快捷键的 id 与写法打包成 `HotkeySpecs` |
| `hidden_window.rs` | 隐藏顶层消息窗口：系统广播 + 五个全局快捷键的注册（必须在有消息队列的线程上做） |
| `clipboard.rs` | 往系统剪贴板写文本（"点击当前显示复制路径"用），失败重试、成败都明确 |
| `folder_picker.rs` | 系统自带的选目录 / 选图片对话框（`SHBrowseForFolderW` / `GetOpenFileNameW`），带属主窗口 |
| `environment.rs` / `info.rs` / `logfile.rs` / `com.rs` / `error.rs` | 诊断、日志、COM 初始化 |
| `desktop_layer.rs` / `video*.rs` / `audio.rs` | **视频相关：外壳已删除，模块保留但无人调用**（见 §8） |

## 3. 便携化与数据目录

所有数据放在一个目录里，整个文件夹拷到哪都能跑。

解析顺序（`paths.rs`）：

```
1. 环境变量 WWP_HOME（明确指定，优先级最高）
2. 程序所在目录           ← 便携模式（交付版走这条）
3. 开发期项目根目录       ← 向上找 tauri.conf.json（cargo run 时走这条）
4. %LOCALAPPDATA%\WindowsWallPaper   ← 都不可写时的兜底
```

第 2、3 步会**实际写一个探针文件再删除**来确认可写。
只检查"目录存在"是不够的：`Program Files` 下的目录存在但不可写，
而那种情况下程序会在第一次写配置时才失败。

回退到第 4 步时界面会显示原因（`fellBack` / `fallbackReason`）——
用户需要知道他的数据没放在自己以为的地方。

根目录下会生成 `wwp-data-location.txt`，内容是可读的说明（数据根目录、
来源、程序目录）。**它本身就是"数据确实在程序目录"的证据**。

### 交付形态

`release\WindowsWallPaper\` 是一个可直接拷走的文件夹。
首次运行生成 `data/`、`logs/`、`webview2/`、`wwp-data-location.txt`。

**打包时要保留 `config/`**：那里面是用户自己调的设置，重建不出来。
`scripts/build-package.ps1 -CleanData` 清运行时数据但保留 `config/`。

## 4. 图库索引

**为什么用 JSONL**：一行一条记录，因此可以逐行读、按需解析，
不必把整个索引反序列化成内存结构。万级图库下这是关键。

`data/index/<图库ID>/index.jsonl`，每行：

```json
{"p":"F:\\...\\a.jpg","w":3840,"h":2160,"sz":1234567,"mt":1699999999,"or":1}
```

`or` 是方向（EXIF orientation）。**长宽比必须用方向修正后的值**，
否则竖拍的照片会被当成横图。

写入是**原子**的：先写 `index.jsonl.tmp`，再 `rename` 覆盖。
这样断电或崩溃不会留下半个索引（那会让下次扫描"全部重探"或读出错行）。

扫描分两个阶段，进度分开上报：

1. **遍历**——递归列目录，收集候选文件。开销几乎全在**目录**上
   （每个目录一次 `read_dir`）。
2. **探测**——读取每个文件的头部长宽高。开销在**文件数**上，可并行。

这两个阶段的耗时差异很大（实测数据见 §9），因此进度上报按
"目录数 + 时间"双触发，而不是按文件数（理由见 `AGENTS.md` §10.6）。

### 增量重扫：复用、以及"变了什么"

重扫时**未变化的文件不会被重新打开**：判据是旧记录里的
`(路径, 大小, mtime)` 与磁盘现状一致。这直接决定了几万张图库的成本——
遍历仍然要走一遍，但探测阶段可以整批跳过。

索引头（`index.meta.json`）除了"这次打开了几个文件"（`reused_entries` /
`probed_entries`），还记三个**变化台账**：`added`（旧索引里没有）、
`updated`（有但大小/mtime 变了）、`removed`（旧索引里有、这次没出现在候选里）。
用户问的是"我的图库变了什么"，而"重探了几个"把"新加的图"与"改过的图"
混在一起，答不了这个问题。

### 一键重扫全部图库

`library_scan_all`（无参数）：读当前图库清单，在**一个**后台线程里**串行**
扫每个库，每个都用增量。结果逐库列出，走 `wwp://scan-all-done` 事件
（单个图库扫完走的是 `wwp://scan-done`，两者语义不同）。

- 一个库失败（目录不在、盘没插上）**不影响其余**，只有"取消"会中断整批；
- 取消是"当前这个库收尾之后停"；
- 进度多两个数字（第 i 个 / 共 N 个），界面上与右上角浮窗里都显示。

实现在 `commands::run_one_library_scan`（单个图库）与 `library_scan_all`
（批循环）——单库扫描与扫全部共用前者，避免两条路各写一份进度上报。
理由见 `AGENTS.md` §10.31。

## 5. 设置模型

`config/settings.toml`。**字段归属分两层**——这是这套模型的核心设计：

```
图库清单（顶层 libraries[]）      内容来源
  一个放图片的根目录一项；顺序 = 用户添加的顺序

播放列表（[[playlists]]）        内容相关
  id, name, libraries[], interval_seconds, fit_mode

显示器（[monitors."<屏幕名>"]）   物理属性
  current_playlist,
  [filter] aspect_min / aspect_max / min_width / min_height

（显示器上**没有**"是否参与轮播"字段：不想让某块屏换纸，就不给它设 current_playlist）
```

**为什么这么分：**

- 间隔 / 填充方式属于**内容**——一套精选图想慢慢看，
  一套随手拍的可以快翻。因此它们跟着列表走。
- 长宽比等筛选属于**屏幕**——竖屏就该只留竖图，换列表不该改变这一点。
  因此它跟着显示器走，所有列表共用。

这是用户明确选的分工，有测试守着
（`interval_and_fit_come_from_the_playlist_not_the_monitor`）。

### 图库与播放列表的两层分工（**这一条被用户改过**）

- **图库是独立配置项**（顶层 `libraries[]`）：一个图库就是"一个放图片的根目录"。
  增删的入口**只有**「图库」页的「新增图库 / 移除」按钮。
- **播放列表只勾选已有的图库**。用户明确要求"取消通过播放列表新增图库"：
  加一个图库不该先绕到某个列表里去打开它。
- 因此**允许**一个图库暂时不被任何列表引用（刚加进来就是这样）：它不会被播到，
  图库行上标成「未被使用」。这不再是"不该出现的半截状态"，而是配置过程的正常一步。
- 移除一个图库时，引用它的播放列表会**一并解绑**——不解绑的话，下次读盘时
  `Settings::adopt_missing_libraries` 会把那个目录补回清单，用户看到的是
  "我移除了它，重启又回来了"。**磁盘上的文件与 `data/index/` 下的索引都不删**：
  再用同一个路径加回来时可以直接复用索引，不必重扫几万个文件。
- **旧配置会被补齐**：图库原先是从播放列表汇总出来的，因此用户手上的旧
  `settings.toml` 里没有 `libraries` 这一行。读盘时会做一次幂等合并
  （被播放列表引用的一定在图库清单里），否则升级后图库页会是空的。
- **图库的"启用/禁用"开关已删除**（用户要求）。
- **没选播放列表时不产生任何候选**，而不是"退回用全部图库"。
  后者会让一块屏在用户还没配置时就开始播他没指定的图。
  界面会明确显示"还没选播放列表"，因此提示与实际行为一致。
- **删除列表时自动清空指向它的绑定**。不清的话那块屏会"选了但找不到"，
  界面显示"已选 list3"而实际没有内容，很难查。

### 长宽比是半开区间 `[下限, 上限)`

含下限、不含上限。这样相邻区间能**无重叠拼接**：
一屏 `[1.3, ∞)`、另一屏 `[0, 1.3)` 正好把所有图分完、不重不漏。

若两端都包含，比值恰好 1.3 的图会同时落进两块屏。

界面上的说明文字通过**跟随鼠标的悬浮提示**给出（`Tooltip.tsx`），不占版面。

### 换纸节拍：每屏各自到点，各自换，谁也不等谁

计时仍由外壳的调度线程统一驱动（`Playback::time_until_next` 决定何时醒来），
但到点后的做法变了：`Playback::claim_due` 只把**该换纸的屏取出来**，
外壳为每块屏各起一个短命线程去换，**不等它们做完**。

> **这条是用户改过的要求。** 最初他要的是"两块屏同时换、快的等一下慢的"，
> 那时 `tick` 用 `thread::scope` 并行换并 `join` 全部。后来他发现两块屏可以各自
> 暂停/继续，而"等齐"与"独立"互相牵制（一块被暂停时，另一块还在按节拍等它），
> 于是明确取消同步。现在间隔相同的两块屏仍会落在相近的时刻——那是设置的
> 自然结果，不是被强行对齐的。

「下一张 / 上一张」这类**手动**操作仍然并行等齐（`run_parallel`）：
点一下就是要"都换上去"，与"到点自动换"不是同一件事。

每块屏另有自己的 `paused` 位（`pause_screen`），与全局暂停是"或"的关系——
这样"只让副屏停下来"不需要动播放列表。

### 只有随机：最近 10 个名字

顺序与倒序两种播放方式已被用户取消。随机的语义也定死了（`playback/select.rs`）：
**不保证一个周期不重复、不记整套顺序，只记最近 10 张的名字**（只记名字，不记图像）。

挑选时从随机起点向后找第一张不在那份名单里的；候选比名单还少时接受重复。
名单只活在内存里、随播放计划重建，因此每次「重新加载」都是新的一轮随机。
### 两种"这块屏不轮播"

| 做法 | 字段 | 行为 |
| --- | --- | --- |
| 不给它选播放列表 | `current_playlist = ''` | 没有候选，永远不换纸 |
| 固定单图 | `single_image = '<图片路径>'` | 只显示这一张，不轮播；**优先于播放列表** |

固定单图的产物写成 `data/output/<屏>-single.bmp`：**只有一份**，
换了源图就覆盖它（mtime 比较，与 NSFW 壁纸同一套判断）。
它在计划里是一个独立的形态（`ScreenPlan::single_image`），
既不进"到点"集合、也不会被"下一张/上一张"带上——否则每个间隔都会把同一张图
重新解码并设一遍。

### NSFW 模式：固定壁纸 + 预解码

每屏一个 `nsfw_wallpaper`；产物固定写成 `data/output/<屏>-nsfw.bmp`，
与轮播用的两个槽位**不共用文件名**。启动时与改设置后在后台先把它按屏裁好，
点击/快捷键那一刻只剩一次 `SetWallpaper`。是否复用已有产物要**两条同时成立**：产物不比源图旧（mtime），**且**产物旁边那份 `.src` 记录写的还是这张源图——只看 mtime 会在
状态（"现在处于 NSFW 模式"）记在 `data/nsfw-state.json`，启动时优先读它。

**处于 NSFW 模式时改 NSFW 壁纸**：后端除了准备新图的缓存，还会**立刻把新的那几张切上去**
（`PlaybackManager::reapply_nsfw`）。只解缓存不切换的话，屏幕上仍是旧图，
用户看到的就是"我改了但它没变"——他报的正是这个。
此时**不再调 `prewarm_nsfw`**：两条路会同时写同一个产物文件。

### 全局快捷键：五个，共用一个消息窗口

`nsfw_hotkey` / `pause_hotkey` / `next_hotkey` / `previous_hotkey` / `show_window_hotkey`，
默认 `Ctrl+Alt+S` / `P` / `Right` / `Left` / `W`。注册必须在拥有消息队列的线程上做，
因此统一在 `hidden_window` 那个隐藏顶层窗口里注册（`WM_HOTKEY` 只投递给注册它的窗口），
按 **id** 分发到五个动作上，动作都复用界面按钮（或托盘）走的同一段逻辑。

其中「显示主界面」不碰壁纸、也不改播放状态，只是把设置窗口显示出来
（`tray::show_main_window`：show → unminimize → set_focus），与托盘菜单的
「打开主界面」、第二次启动程序是同一条路——程序默认不显示主界面时，它是比找托盘图标
更直接的一条入口。

解析器支持"有名字的键"（`Left` / `Right` / `Space` / `PageUp` / `Esc` …），
因为"上一张/下一张"绑方向键才自然。写错或被别的程序占用都只记一条 warn，
不影响启动，也不会阻止保存。

### 排除规则是前缀匹配

`exclude.dirs` 命中则**整棵子树跳过**。目录树界面上的
"取消勾选父级 = 子级全不参与"就是复用它实现的。

**只有这一条规则**：原先的 glob 与正则、以及专门的一个「排除规则」界面页
都已按用户要求删除（他只通过图库页的目录复选框排除目录）。少一套语法、
少一个页面、少一类"用户说不清哪条在起作用"的排障场景。

一个衍生细节：`FolderNode` 里 `excluded_here`（用户显式取消）
用**精确**路径比较，而 `included`（实际生效）用会向上查找的匹配器。
因此界面能区分"用户显式取消"与"随上级被取消"。

## 6. 壁纸呈现层

**采用逐屏独立设图（`IDesktopWallpaper::SetWallpaper`），不合成虚拟桌面大图。**

| 路线 | 做法 | 代价 |
|---|---|---|
| **A. 逐屏设图**（采用） | `SetWallpaper(monitor_id, path)`，每屏一张图 | 每次换图触发一次系统过渡动画；只支持静态图 |
| B. 合成虚拟桌面大图 | 每屏画进同一张位图，`SystemParametersInfoW` 一次送出 | 双 4K = 7680×2160，BGRA 约 **63 MB/帧**；任一屏换图都要重合成整张，**两屏的切换时机被强制绑定** |

选 A 的决定性理由是最后那条：路线 B 下两块屏无法独立换图，
而"每屏独立"正是这个项目的核心。

参考实现的逐项对比（Lively / KokoroPaper / FeatherWall 各自借鉴了什么）
见 [`技术备忘.md` 第 1 节](技术备忘.md)。

**显示器身份**：本项目自建屏幕标识（`\\.\DISPLAY1` 这类 `szDevice`），
不用 Tauri/tao 给的 monitor id——后者在 Windows 上被报告为不可靠
（[tao#1102](https://github.com/tauri-apps/tao/issues/1102)），
而每屏配置必须跨重启稳定对应到同一块屏幕。理由与实测细节见
[`技术备忘.md` 第 2 节](技术备忘.md)。

### 不做还原：程序本体不记忆任何壁纸

**程序不会把用户的壁纸还原回去。** 原先那套"开始前拍快照 → 停止/退出时按快照还原
→ 崩溃后下次启动补还原"的机制已整体删除（连同 `data/wallpaper-snapshot.json`、
「停止并还原壁纸」按钮、以及两个实测入口）。

留在这里的是一条通用知识（`wallpaper/mod.rs` 仍然提供 `snapshot` / `restore`，
只有 `--rotate` / `--spike-wallpaper` 这类**实测工具**在用）：

`SetWallpaper` 对**不存在的设备路径静默返回成功**。因此真要还原时不能只按
设备路径找，还要按屏幕矩形兜底——否则显示器重插之后还原会静默失败。
另一个坑：壁纸回读有约 230 ms 延迟，设完立刻回读会拿到旧值，
因此不能用"设完回读比对"判断成功。

### 静态与视频的互斥（做视频时必须读）

24H2+ 上 `SPI_SETDESKWALLPAPER`（`IDesktopWallpaper::SetWallpaper` 同理）
会**销毁 WorkerW**，而视频层的宿主窗口正挂在里面。正确顺序是：

```
先设兜底壁纸 → 再挂载宿主窗口 → 挂载期间不再触碰系统壁纸
→ 退出时先卸载窗口 → 再恢复用户壁纸
```

细节与实测见 [`技术备忘.md` 第 3 节](技术备忘.md) 与风险 R9。

## 7. 界面与日志

### 界面结构

```
播放    运行控制（含「重新加载」）、启动与窗口开关、每屏一张卡片（左右两列并排）
图库    图库清单（新增/移除图库）→ 扫描 → 目录树勾选 → 播放列表（增删改 + 勾选图库）
排除    全局排除规则（只有目录前缀一类）
设置    数据目录、诊断导出、关于
```

**每块屏的设置在左右两列里并排**（`repeat(auto-fit, minmax(320px, 1fr))`）：
两块屏的筛选条件常需要放在一起对比（一屏留横图、一屏留竖图，边界要拼起来），
上下堆叠就得来回滚。窄窗口下自动退化成单列，不需要媒体查询。

**界面不堆文字**：较长的解释放在跟随鼠标的悬浮提示里。

### 启动与退出

启动时**自动接管壁纸并开始轮播**（`general.auto_start`，默认开启），
但**尊重上次的暂停状态**：用户主动暂停过就保持暂停。

那份"上次是不是暂停"存在 `data/playback-state.json`，**不写进
`settings.toml`**——它是运行时状态而非用户设置，写进配置会让它在界面上
变成一个看起来可编辑、实际没意义的字段。

记录点只有一处：`run_manager` 处理 Pause/Resume 命令的地方。暂停有三个
入口（界面按钮、托盘菜单、启动时的自动开始），它们最终都变成发进同一个
通道的命令——集中在一处才不会漏。

完全退出时**什么都不做**——程序不还原壁纸（用户明确要求，快照/恢复机制已整体删除）。

### 扫描状态的唯一来源

`frontend/useScanWatcher.ts` 是扫描状态的**唯一**数据来源，
页面与右上角浮窗都用它。

这不是洁癖，是为了避免一类很难查的 bug：原先页面用事件（`listen`）、
浮窗用轮询命令（`invoke`），两套机制。结果 `capabilities/` 缺失时
事件被静默拒绝，于是**浮窗正常、进度条永远停在「正在准备」**。
详见 `AGENTS.md` §7.2。

### 日志

`logs/app.log`，按大小滚动。分级：

| 级别 | 用途 |
|---|---|
| `log_error` | 真的出错了，用户需要知道 |
| `log_warn` | 异常但可继续（例如跳过不存在的图库） |
| `log_info` | 关键状态变化（启动、开始/停止轮播、扫描完成） |
| `log_debug` | 诊断细节（几何计算、状态轮询）。**默认不写盘** |

诊断信息不能冒充错误：混用会让 `[ERROR]` 过滤失去意义，
而排查问题时第一件事就是过滤错误。

## 8. 视频壁纸：功能与外壳接线都已删除

**界面、命令、外壳接线全部删掉；`wwp-core` 里的实验模块保留，但已无人调用。**

原因是技术性的：视频需要在每块屏上创建一层铺满的**不透明**宿主窗口
来画帧（DirectComposition）。图片壁纸由系统渲染，完全不需要它。
**如果为了视频无条件建出那层窗口，它会盖住系统壁纸——用户看到一片灰色。**

项目最初就踩了这个坑：`playback_start` 无条件挂载桌面层，
表现为"壁纸变灰、停止时闪一下"。

做成开关而不是删掉代码，是为了保留已经调通的整条链路
（DComp 视觉树、Media Foundation 解码、音频、音画同步）——
重新踩一遍那些坑不划算。全部记录在 [`技术备忘.md` 第 3 节](技术备忘.md)。

验证图片模式确实没建窗口的方法：

```powershell
pwsh -File scripts\probe-layer-windows.ps1
# 期望："没有任何宿主窗口——此时屏幕应当显示正常的系统壁纸。"
```

## 9. 性能目标与实测

| 指标 | 目标 | 实测 |
|---|---|---|
| 万级图库扫描 | 不卡界面 | 6444 张首次全量 141 s，进度实时可见、可取消 |
| 内存 | 不随图库规模线性增长 | 索引按需加载，只解码当前一张 |
| 换壁纸延迟 | 用户感知不到卡顿 | 平均 454 ms、最高 849 ms |
| 长时运行 | 无泄漏 | 混合图库 5 分钟：内存谷底稳定 88→101 MB，无单调上升 |

**几个改变了设计判断的实测结论：**

- 遍历耗时由**目录数**决定，不是文件数：

  | 目录 | 目录数 | 文件数 | 遍历 | 探测 |
  |---|---|---|---|---|
  | `D:\Projects` | 41,734 | 363,580 | 4.7 s | 0.6 s |
  | `C:\Users\<用户>` | 35,799 | — | **29.9 s** | 4.9 s |
  | `C:\Program Files` | 8,214 | 90,637 | 1.1 s | 1.1 s |

- 热缓存下并行度几乎无影响（4/8/12/16/24 线程探测耗时 456–572 ms，
  无单调趋势）。因此线程数取 `cores.clamp(1, 12)` 即可。
- **逐帧换壁纸做动画不可行**：每次换纸平均 454 ms，8 帧就是 3.6 s。
