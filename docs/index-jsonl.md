# 扫描产出的索引文件：`index.jsonl` 与 `index.meta.json`

> 什么时候读这份：想直接打开索引看里面到底存了什么、或者要写脚本处理它的时候。
> 界面上的对应说明是图库页「已建索引」标签的悬浮提示。

## 这两个文件在哪里

每个图库（播放列表里关联的一个根目录）各有一套，目录名由图库路径算出的
FNV-1a 哈希（16 位十六进制）决定，因此**同一路径永远得到同一个目录名**，
路径大小写差异不会产生两份：

```
data/index/<图库id>/
├── index.jsonl        每个文件一行 JSON
└── index.meta.json    这次扫描的统计与耗时
```

`<图库id>` 可以从 `--diagnose` 的输出或界面上的索引统计里对上——它本身
不含可读的路径信息，所以想确认某个目录对应哪个 id 时，用
`data/index/*/index.meta.json` 里的 `root` 字段去认。

## 为什么是 JSONL（一行一条）而不是一个大 JSON 数组

1. **可以边扫边写**：扫描过程中不必把全部记录留在内存里；
2. **单行损坏只损失那一行**：解析不了的行会被跳过并记一条警告，其余照常可用；
3. **人能直接看**：出问题时 `Select-String` 或记事本就能查，不需要专门的工具。

写文件走"临时文件 + 改名"：进程中途被杀不会留下半截索引。
索引格式版本（`index.meta.json` 里的 `formatVersion`）不一致时，旧记录会被
视为不可信并触发重扫，而不是勉强解析出一堆错值。

## `index.jsonl`：每行一条记录

字段名是**短名**：一个图库可能有几十万行，键名每短一个字节，省下的就是几十万字节。

| 字段 | 类型 | 含义 |
|---|---|---|
| `p` | string | 图片/视频的**完整路径**。路径分隔符统一成 `/`，因此一个路径可能有两种写法（`D:/Pics/a.jpg` 与 `D:\Pics\a.jpg`）指同一文件。 |
| `w` | number | **显示宽**（像素）。已经按 EXIF 方向换算过：竖拍照片（方向 6/8）的 `w` 是旋转后的宽，也就是**实际看到的宽**。 |
| `h` | number | **显示高**，同上。筛选用的长宽比就是 `w / h`。 |
| `mt` | number | 文件的修改时间，Unix 秒（`modified()` 转换而来）。取不到时为 `0`。 |
| `sz` | number | 文件大小（字节）。 |
| `or` | number | EXIF 的**原始方向值**（1~8，1 = 未旋转）。`w/h` 已经换算过，但真正解码显示时还要再转一次，因此方向必须留着。非法值按 1 处理。 |
| `fmt` | string | **嗅探出**的真实格式（`jpeg` / `png` / `webp` / `bmp` …），不是扩展名。约一成图片的扩展名与内容不符，所以按内容判断。 |
| `ok` | number | `1` = 能被本程序解码，会参与播放；`0` = 认得出格式但没有解码器（例如 HEIC），**只统计不播放**——留着它才能回答"我那个 HEIC 去哪了"。 |
| `kind` | string | `image` 或 `video`。**旧索引里没有这个字段**，读的时候按 `image` 处理（那时索引里本来也只有图片）。 |

`mt` 与 `sz` 一起构成增量扫描的判据：两个都没变就复用旧记录，连文件都不用打开。

一行示例（为便于阅读加了缩进，实际是一行）：

```json
{ "p": "D:/Pics/2024/a.jpg", "w": 4032, "h": 3024, "mt": 1717000000,
  "sz": 2456789, "or": 1, "fmt": "jpeg", "ok": 1, "kind": "image" }
```

## `index.meta.json`：这次扫描的概况

单独放一个小文件，这样"想看一眼统计"不必读几十万行的记录。

| 字段 | 含义 |
|---|---|
| `formatVersion` | 索引格式版本。与程序里的常量不一致时整份索引作废并重扫。 |
| `root` | 这个索引对应的图库根目录。**认 id 靠它。** |
| `scannedAt` | 上次扫描完成时间（Unix 秒）。界面上的"上次扫描"就是它。 |
| `scanMillis` | 这次扫描耗时（毫秒）。 |
| `reusedEntries` | 复用旧记录（未重新打开文件）的条目数。 |
| `probedEntries` | 重新探测的条目数。增量扫描正常时它应该很小。 |
| `removed` | 已经从磁盘消失、本次被移除的条目数。 |
| `stats` | 统计详情，见下表。 |

### `stats` 里的字段

| 字段 | 含义 |
|---|---|
| `files_seen` | 目录里看到的所有文件数（含非图片）。 |
| `files_ignored` | 扩展名不像图片、直接跳过的文件数。 |
| `playable` | 读到尺寸并**可播放**的条目数（**包含视频**，是 `videos` 的超集）。 |
| `videos` | 其中有多少个是视频。视频的播放路径与图片完全不同，因此要能分开数。 |
| `unsupported` | 认得出格式但没有解码器的条目数。 |
| `unreadable` | 打开或解析失败的条目数（文件损坏、权限不足等）。 |
| `excluded` | 被排除规则挡掉的条目数。 |
| `unsupported_formats` | "没有解码器的格式 → 出现次数"的映射。 |
| `unreadable_samples` | 读不了的样本列表（`path` + `reason`），**最多 500 条**。 |

统计守恒关系（排查"数字对不上"时按这个查）：

```
files_seen = files_ignored + playable + unsupported + unreadable + excluded
playable   ⊇ videos
```

`unreadable_samples` 有上限是刻意的：图库里可能有上万个坏文件，
全记进索引只会把索引撑爆。

## 手工处理时的两个注意点

1. **不要手改这两个文件**——索引与应用状态不一致时表现为"某些图突然不播了"
   或"新加的图不出现"。要强制重建，用界面上的「全量重扫」，
   或删掉整个 `data/index/<图库id>/` 目录再扫描。
2. **`p` 里的路径是当时扫描到的路径**。整个图库目录被移动或改名之后，
   索引里的路径就全失效了（表现为"候选 N 张但一张都设不上"）；
   这时重新扫描即可。
